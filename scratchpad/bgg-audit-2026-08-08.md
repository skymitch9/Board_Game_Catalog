## How the score is built

The score is a **weighted average over the evidence that was actually available**, not a sum.
A component whose data is missing on either side contributes to neither the numerator nor the
denominator, so an item with no `year_published` of ours is not punished for a fact nobody
recorded — it is simply judged on fewer signals. Final value is clamped to 0…1.

```
score = Σ(weight × fraction) / Σ(weight, over available components only)
```

| Component | Weight | Always available? |
|---|---:|---|
| Name | 50 | yes |
| Year | 20 | only if both sides have one |
| Publisher | 15 | only if both sides have one |
| Kind plausibility | 10 | yes |
| Corroboration | 15 | yes |

### Fractions

| Component | Fraction | Condition |
|---|---:|---|
| Name | 1.00 | `normaliseTitle` equality with BGG's primary name |
| | 0.90 | `normaliseTitle` equality with a BGG `<name type="alternate">` |
| | 0.80 | `titleSimilarity` ≥ 0.9 |
| | 0.60 | `titleSimilarity` ≥ 0.8 |
| | 0.45 | `titleSimilarity` ≥ 0.7 |
| | −1.00 | below 0.7 |
| Year | 1.00 / 0.50 / 0.00 / −1.00 | exact / off by 1 / off by 2–3 / off by ≥4 |
| Publisher | 1.00 / 0.70 / −1.00 | exact / partial / absent from BGG's whole publisher-link list |
| Kind | 1.00 / 0.50 / 0.20 / −1.00 | matches BGG `type` / adjacent / loose / **family-trap shape** |
| Corroboration | 1.00 | the candidate is in the parent/root id's own `boardgameexpansion` / `boardgameaccessory` link list |
| | 0.70 / 0.50 / 0.30 / 0.10 | sole candidate / 2–4 / 5–9 / ≥10 candidate ids returned |

**`normaliseTitle` and `titleSimilarity` are the shipped functions**, ported verbatim from
`packages/core/src/vision.ts` and `packages/core/src/barcode.ts` — no third metric was invented.
Publisher comparison is the one new thing: it strips corporate noise (`Games`, `Studios`, `GmbH`,
`Sp. z o.o.`, …) and compares against **every** `boardgamepublisher` link, not just the first,
because BGG lists the original publisher alongside every localisation house and our catalog
stores whichever one is on our box.

## The gate that decides PROPOSED from UNMATCHED

Scoring never runs on a candidate that has not cleared a **hard gate**, and the gate is the
reason this audit cannot produce the failure it was commissioned to avoid.

1. **`isFragmentOf(bggName, ourName)` must be false.** This is the shipped rule, verbatim. One
   title's meaningful words wholly inside the other's, with words to spare, is the *"same
   family, different product"* shape — a base game, a sibling, a different edition, a different
   product in the same line.
2. **`titleSimilarity` ≥ 0.7 (`MIN_SPINE_SIMILARITY`)**, or exact equality to a BGG alternate name.

**0.7 and not 0.34.** `docs/HANDOFF.md` records that reusing the forgiving `MIN_TITLE_SIMILARITY`
for unattended matching *caught nothing*, because a one-word fragment of a two-word title scores
`2×1/(1+2) = 0.67` every single time while genuine reads score 1.00. This audit is unattended
matching over 609 rows, so it uses the unattended floor.

**The search widens; the scoring does not.** Queries walk a ladder — full name, then the name
with product-type words dropped, then the subtitle alone, then the family prefix — but every
candidate is scored against the item's **original full name** regardless of what was searched
with. Widening therefore cannot loosen a match; it can only surface more things for the gate to
reject. That is what makes "try like items" safe.

**Alternate names are where "like items" legitimately pays.** BGG's `<name type="alternate">`
nodes are the Catan / The Settlers of Catan mechanism, and an exact match to one of them is
treated as near-exact (0.90). Edition wording and punctuation differences pass through
`normaliseTitle` for free.

## Verdict rules for the 197 rows that already have an id

Verifying an id a person already set is a **different question** from proposing a new one, so
`isFragmentOf` is deliberately *not* a hard gate in this half. *Dead of Winter* vs BGG's *Dead of
Winter: A Crossroads Game* is a fragment relationship **and** the same product — the catalog just
stores the short title. Treating that as broken would have produced 35 false alarms.

What separates a benign subtitle difference from the real family trap is `kind`:

| Situation | Verdict |
|---|---|
| Name matches exactly (or an alternate name does) | **CONFIRMED.** Identity is settled; a `kind`, year or publisher quibble is a *note*. A holofoil box is never named identically to its base game. |
| Fragment relationship **and** our row is a non-`base` child **and** BGG's entry is a base game carrying expansions/accessories of its own | **SUSPECT** — the id may name the family, not the product |
| Fragment relationship otherwise | **CONFIRMED**, with the title difference noted |
| `titleSimilarity` < 0.7 and no fragment relationship | **SUSPECT** — names disagree |
| Year differs by ≥3 (both known) | **SUSPECT** |
| Year differs by 1–2 | note only |
| Our publisher absent from BGG's entire publisher-link list | **SUSPECT** |
| Our `kind` disagrees with BGG's `type` under an exact name | note only |

## What I would apply, and at what cut-off

This is a recommendation, not an instruction, and the owner decides.

**Apply PROPOSED rows scoring ≥ 0.85 — 35 rows, 29 of them owned. Hand-check everything below.**

Two independent checks come back clean on that set, and they are the two that would catch the
failure this audit exists to prevent:

- **Not one of the 35 carries a `sibling_risk` flag.** Every sibling-confusion candidate the
  run produced scored below the line on its own.
- **No BGG id is proposed twice at or above 0.85.** Where several of our rows did converge on one
  id — and 25 groups did — the score separated them every time: the correct row scored 0.85+ and
  its siblings scored 0.63 or less. Not one collision has two rows above the line.

Why 0.85, stated as arithmetic rather than as a feeling. Under the weighted average, the best a
candidate can score for a given name strength — assuming year, publisher, kind and corroboration
all agree perfectly — is:

| Name evidence | Name fraction | Best achievable score |
|---|---:|---:|
| exact / alternate-name exact | 1.00 / 0.90 | 1.00 / 0.95 |
| `titleSimilarity` ≥ 0.9 | 0.80 | **0.87** |
| `titleSimilarity` ≥ 0.8 | 0.60 | 0.82 |
| `titleSimilarity` ≥ 0.7 | 0.45 | 0.75 |

So **0.85 admits exactly two populations**: titles that are the same string, and titles that
differ by ≥0.9 similarity *and* agree on everything else. In this run the second group is
entirely rows where BGG omits or includes the word "Expansion", or punctuates differently —
*Command of Nature: Sand & Wind Expansion* against *Command of Nature: Sand & Wind*. That is the
"like items" case the brief wanted used, and it is the whole reason not to set the bar at 1.00.

Below 0.85 sit the rows that are genuinely a judgement call, and the run produced real examples
of why they must not be applied blind:

| Row | Proposed | Score | Verdict on inspection |
|---|---|---:|---|
| 502 *Unstable Unicorns: Christmas Expansion Pack* | Unstable Unicorns:  Nightmares Expansion Pack | 0.78 | **wrong sibling** — same family, different product |
| 218 *Moonrakers: Frontier Micro-Expansion* | Moonrakers: Vanguard Micro-expansion | 0.54 | **wrong sibling** — same family, different product |
| 294 *Here to Slay: KS Exclusive Monster Expansion Pack* | Here to Sleigh: A Here to Slay Expansion Pack | 0.63 | **wrong sibling** — same family, different product |

Every one of those is a *sibling inside the correct family*, which is the failure the gate cannot
catch on its own — both products really are in the family, so family corroboration argues for the
wrong answer. The score is what separates them, and 0.85 is above all three.

Why not higher: 0.95+ requires our side to hold a year **and** a publisher, and most of the 609
rows with no `bgg_id` also have no publisher — largely the same population. Raising the bar would
reject rows for a fact nobody ever recorded rather than for anything BGG said.

**Nothing in SUSPECT should be applied.** Those are 5 rows to look at, not 5 rows to change.

**And nothing here should be applied in bulk without the TSV being read.** The score orders the
work; it does not replace the look.

### ⚠️ Do not fix this by adding `pack` to `GENERIC_TITLE_WORDS`

One row in that very table is a genuine family trap, and it is the argument against automating
this:

> **277 `Casting Shadows: Expansion Pack`** was rejected against **[359502](https://boardgamegeek.com/boardgame/359502) *Casting Shadows*** for differing only by
> the word "pack". But *Casting Shadows* is the **base game** and our row is its expansion pack.
> Attaching that id is precisely the failure this audit was commissioned to prevent.

So the same textual pattern contains ~19 near-certain matches **and** at least one wrong-product
match, and no rule reading only the two strings can separate them — the thing that separates them
is knowing that *Casting Shadows* is a base game. That is a human judgement, and it is why this
list is offered as **a short manual worklist, not a threshold change**. Widening the generic-word
list would silently convert that one row into a wrong id, which is the exact shape of the bug the
handoff records at 0.34.

Worked by hand at roughly ten seconds a row, this is the highest-value twenty minutes available
after the 35 — and unlike the 35, most of it is `expansion` rows, which is what the completeness
feature actually needs.

## Where I am least sure

- **Publisher comparison is the weakest signal in the whole scheme.** It is the one metric not
  ported from shipped code. Our catalog stores one publisher; BGG lists up to fifty, including
  every localisation house, and normalising `Sp. z o.o.` and `Games` out of both sides is a
  heuristic I wrote today. It carries only 15 of the weight and it never gates anything, which is
  deliberate — but a `PUBLISHER` disagreement in the TSV deserves less alarm than a `NAME` one.
- **`kind` plausibility encodes a taxonomy disagreement, not an error.** BGG types Dice Throne
  heroes and King of Tokyo Monster Packs as `boardgameexpansion`; the catalog calls them `base`.
  Ten CONFIRMED rows carry that note. Neither side is wrong and nothing needs changing.
- **A false UNMATCHED is cheap and a false PROPOSED is not**, so the gate is tuned to produce the
  former. Some rows in UNMATCHED certainly do have BGG entries under a name I did not think to
  search for. The `near_miss_rejected` column is where to start looking.
- **The year on a `wanted`/`preordered` row is a guess on both sides.** Unreleased products move
  years; BGG's figure and ours can disagree without either being wrong.

  --command "SELECT ... FROM item i ORDER BY i.id" > scratchpad/bgg-audit/catalog.json

# 2. the audit

⚠️ **The one place this client deliberately departs from the shipped one is the rate limit.**
`packages/bgg/src/client.ts` uses a flat 1.1 s gap and gets away with it because every call goes
through Cloudflare's edge cache with a 7-day TTL. An uncached 1,473-call audit does not: BGG
started answering **429** about ninety seconds in. The gap here is therefore adaptive — 2.2 s to
start, ×1.4 on every 429 up to a 6 s ceiling, decaying back toward 1.6 s after 40 clean calls.
It settled around 2 s and absorbed 10 rate-limit responses without a single lost row.

⚠️ **A 429 must never reach the caller as "no results."** The first version of this client threw
on 429 and the caller treated the throw as an empty result set, which would have written false
`UNMATCHED` verdicts into the map indistinguishable from real ones. Rate limits are now retried
inside the client, and a call that genuinely fails produces an `ERROR` verdict, never `UNMATCHED`.
That distinction is the difference between a map you can trust and one you cannot.

⚠️ **`curl` cannot reach the network in this environment (exit 43) and `Invoke-WebRequest` hangs
on BGG's 401 challenge.** Node's `fetch` works fine and is what the audit uses. `BGG_API_TOKEN`
is read from `apps/worker/.dev.vars` at runtime and is never printed or written anywhere.

**Run cost:** `1473 BGG calls (10 were 429 retries, 0 were 202 retries, 0 failed outright), final gap 1969ms, 57.1 minutes`

## Two corrections made mid-run, recorded rather than quietly applied

Both were found by reading the first hundred rows while the run was still going, and both are
applied by `rescore.mjs`, which recomputes scores from the stored component phrases and makes no
network calls.

1. **The `kind` family-trap penalty was firing on exact name matches.** It dragged
   *Boss Monster: Rise of the Minibosses* — a name BGG matches character for character — down to
   0.66, because BGG types it `boardgame` while the catalog calls it `expansion`. That is a
   taxonomy disagreement, not a wrong id. A different product is never named identically to its
   base game, so an exact name makes the trap impossible; the penalty now only applies when the
   name is *not* exact. This is the same rule the Phase A side already used.
2. **Nothing caught wrong siblings**, so `sibling_risk` was added. It is a flag, not a rejection.

Neither correction loosened the gate. The first raised some scores that were unfairly low; the
second added a warning column. No candidate became eligible that was not eligible before.
